## Correction applied (P1)

The previous wording in `docs/stability.md` and `docs/versioning.md` allowed
"new JSON fields" in a minor release while the published schemas reject
unknown fields. Both documents now state the approved stability-preserving
rule:

- A minor release may add commands, constants or optional arguments whose
  defaults preserve existing behaviour.
- An existing strict schema version (lock 2, manifest 2, receipt 1,
  registry 1) and the default CLI receipt shapes do not gain fields within
  1.x. Additional formats or semantics require a separately versioned,
  explicitly opt-in interface that preserves every existing stable surface.
- Removal and incompatible change wait for 2.0 (documented deprecation, at
  least one minor release and 90 days, unchanged).
- A new replay engine arrives only in a minor release as an explicitly
  selected option; existing engines, their semantics and default behaviour
  are preserved; evidence is interpreted through the engine recorded in its
  lock and never reinterpreted under a newer engine.
- Reviewed exact-fingerprint registry entries for an existing engine remain
  permitted in patch releases (unchanged from 02R2).

The SemVer table in `docs/versioning.md` moves "adding a field to an existing
strict schema version or default receipt shape" to the 2.0-only row and lists
the explicit-selection engine rule and opt-in-interface rule in the minor
row. `docs/stability.md` "What STABLE means" and "Supported replay engines"
carry the same text and link the new ADR.
