## Goal

Let Actseal qualify any model, without weakening what an ACT means:

1. `recorded` provider: the user brings a file of predictions (`case_id`, `choice`,
   `score`, optional `probabilities`). No model call.

   configurable endpoint and model, so any Jev-compatible server works
   (for example a local one).

## Interface contract

### `recorded`

- Input file: LF-delimited JSONL, one row per case:
  `{"case_id": str, "choice": str, "score": number, "probabilities": {label: number}?}`.
  Unknown keys are rejected. A row may instead be
  `{"case_id": str, "failure_code": <existing failure code>}`.
- The adapter stores the row's answer verbatim as `body_json`
  (`{"type":"choice","choice":…,"score":…[,"probabilities":…]}`); replay
  re-normalises from that body.
- Normaliser rules for provider `recorded` (pure, in `normalization.py`):
  1. `score` must be a JSON number (not a boolean), finite, in [0, 1].
     Missing, wrong type or out of range → `ProviderFailure`, never an answer.
  2. `choice` not among the question labels → the existing unknown-choice path.
  3. If `probabilities` is present: keys equal the question labels exactly,
     each value in [0, 1], total within the fixture tolerance of 1, and
     `score == probabilities[choice]` exactly. Any defect → `ProviderFailure`.
  4. The gating value is the raw `score`, bit for bit. It is never renormalised
     and never taken from any other field.
- `ChoiceAnswer` is relaxed: `probabilities` may be empty (score-only answer) or
  a full valid map as today. Nothing else changes; all existing evidence must
  still decode and replay identically. Update the published JSON Schemas under
  `docs/schemas/` to match, and say so in `docs/stability.md` and
  `docs/migration.md`.
- Every `recorded` run carries the warning/note text
  `recorded: provider faults not tested`. Decide, by reading `faults.py` and
  `assessment.py`, how the six canonical fault checks apply when there is no
  live provider: they must not be silently reported as passed. Propose the
  smallest honest handling in your REPORT and implement it (a distinct
  inventory entry or reason code is acceptable; pretending they ran is not).
- `ModelIdentity` for recorded runs: provider `recorded`, model and revision
  supplied by the user (`--model`, `--revision`, required), artifact hash = the
  SHA-256 of the predictions file.

### `decision-api`

- Same wire format, limits, single attempt, no retry, no redirect, credential
  echo guard and status mapping as the Jev transport. Reuse the code; do not
  duplicate it.
- New inputs: endpoint URL (`https://…`, or `http://` only for `localhost`,
  `127.0.0.1` or `[::1]`), model name, and an optional name of the environment
  variable that holds the API key (never the key itself; no key is required for
  loopback). Endpoint and model are part of `ModelIdentity` so a lock binds them.
- Normalisation: the existing Jev normaliser rules, unchanged.
- It stays PROVISIONAL and behind `--experimental-provider`, like `jev`.
- The existing `jev` provider keeps working exactly as today.

### CLI

- `--provider recorded --responses FILE --model NAME --revision REV` on the
  existing commands that take a provider.
- `--provider decision-api --experimental-provider --endpoint URL --model NAME
  [--api-key-env NAME]`.
- Existing options, receipts and exit codes are unchanged.

## Amendments after Codex co-plan review (13 Nov 2026) — these override the text above

1. `decision-api` normalisation: `normalization.py` pins the response model to
   `jev-1.13.0`. For `decision-api` only, match the response model against the
   model locked in `ModelIdentity`; `jev` behaviour stays byte-for-byte as it is.
2. Endpoint goes in the existing `ModelIdentity.runtime` map, as the Jev
   transport already does. No new record field. `revision` for `decision-api`
   is a required user-supplied string (`--revision`).
3. Absent credentials are represented explicitly (`None`), never as `""`: an
   empty string would make the credential-echo guard match every response.
4. Empty `probabilities`: allow exactly empty OR 2..16 entries, never one.
   Update both `decision-record.schema.json` and `fault-result.schema.json`.
   Use a separate recorded normalisation branch; historical renormalisation
   for existing providers is unchanged; probabilities are never fabricated.
   Make conformance expectations profile-specific where they assume diagnostic
   confidence or ignored fields that `recorded` lacks.
5. Fault checks: keep all six. They already use synthetic captures and call no
   provider. Generate recorded-shaped fault bodies; existing providers' fault
   bytes are unchanged. Add the required warning on recorded captures and a
   recorded-only note surfaced through replay's existing notes. Status, counts
   and bounds are preserved. Claim no upstream provider-fault coverage.
