## Co-planning choices

1. **Inputs and output layout.** Both commands take the ordinary contract
   TOML and existing provider flags; its template threshold is ignored during
   selection and omitted from the plan. `--out` is a new root containing
   `calibration/` (exactly the five required files) and, only on selection,
   `contract.toml`. Qualification adds `lock.json`, `evidence/` and
   `qualification.json`. Verification size is the complete supplied split's
   row count, never a truncated subset. IDs and exact state texts must be
   disjoint, preserving the existing leakage rule.
2. **Selection defaults and captures.** Fixed grid
   `[0.5, 0.6, 0.7, 0.8, 0.9, 0.95, 1.0]`; target `0.8`; selection tail `0.05`.
   User grids are frozen before provider construction. Stored decisions use
   the lowest grid threshold. Eligibility uses existing `evaluate` at the
   smallest positive binary64 threshold, so failures, fallback, disallowed
   choices and score zero cannot enter ACT counts. Scores otherwise remain
   unchanged; no policy precedence is duplicated.
3. **Publication and links.** Seal and close the plan file in a sibling staging
   directory before the first `decide`; publish the complete root through the
   existing exclusive rename. Reuse evidence byte-budget, row encoding and
   exclusive-write helpers; remove staging captures on every failure. Plan
   and manifest have canonical self-hashes. The qualification receipt links
   the SHA-256 of the exact manifest file bytes, the existing lock seal and
   the full existing verdict. Revalidate the sidecar after verification before
   writing that receipt. Derived TOML preserves all fields except threshold,
   including escaped DEL and non-BMP Unicode.
4. **Replay and receipts.** New schema-1 interfaces are separate from lock and
   bundle schema 2 / engine v1. Selection replay requires the exact producer
   fingerprint, with no new compatibility registry. Reconstruct requests,
   normalization and policy decisions from captures; compare counts, grid,
   reason and selected threshold exactly. Only predicted probabilities use
   `math.isclose(rel_tol=1e-9, abs_tol=1e-10)`. Hashes do not authenticate
   sampling, labels, execution or precommit chronology. Successful planning
   reports `PLANNED`; calibration/replay-selection report `SELECTED`; only
   existing verification supplies PASS. Unreachable planning/no threshold
   exits 2; invalid evidence exits 3. Publish five strict schemas and retain
   all existing receipt shapes.
5. **Synthetic demo.** Four additional package resources contain 64 calibration
   and 100 separate verification cases, authored correct responses at score
   `0.95`, risk limit `0.2`, coverage floor `0.5`, alpha `0.05`. The unchanged
   verifier produces PASS. `demo --qualify` without `--out` uses a persistent
   temporary directory; historical `demo` still requires `--out`. Preserve
   the eight historical resource byte checks and add explicit new inventories.

## Review fix

Selection replay now applies the same compatibility rule as bundle replay:
the plan records `implementation_sha256` and `replay_engine_version`; its
engine must be supported, and replay accepts the exact running fingerprint
or two fingerprints explicitly registered for that engine. Because
`check_replay_compatibility` accepts only a `PlanLock`, the small private
`qualification._check_replay_compatibility` helper uses the existing
`compatibility.load_registry()` and `CompatibilityRegistry.engine_for()`.

any response, regardless of registry entries. This supersedes the exact-source-only
selection replay description and limitation above.
