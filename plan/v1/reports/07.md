### `examples/action_gate/`

- `gate.py` (application code, imports only public `actseal` names):
  `Ticket(ticket_id, text)` with no label field; `LocalQueue` (in-memory
  journal of `(queue, ticket_id)` operations, the only action executed);
  `ActionGate(lock, verdict, model, *, expected_lock_sha256)` which refuses to
  open (`GateClosedError`) unless the lock seal equals the expected digest,
  `validate_lock` passes under the running implementation, the verdict is for
  that lock and is `PASS`, and `model.identity()` equals the locked identity;
  `decide` builds `DecisionRequest(ticket_id, text, locked question)`, calls
  `model.decide(..., timeout_s=REQUEST_TIMEOUT_S)`, `normalize(capture,
  question, lock.model_identity)` and `evaluate(outcome, lock.contract.policy)`;
  `route` dispatches `ACT -> queue.enqueue(choice, ticket_id)`, `ABSTAIN ->
  held_for_review`, `ESCALATE -> escalated`, `DENY -> rejected`, as four
  explicit methods, only the first of which has an effect; `route_all` routes
  in order and lets any provider or queue exception propagate (no retry, skip
  or downgrade).
- `run.py`: `--check`, `--route`, `--record DIRECTORY --source-commit SHA`;
  exit 0/1/2. `--check` runs a fresh lock/verify/replay of the authored data in
  a temporary directory, opens the gate on the fresh lock and verdict, routes
  the tickets against the authored expectation table (action, reason, queue,
  `executed`) and the expected queue journal, then checks every recorded run
  (below). Strict `tickets.jsonl` loader (exactly `ticket_id`, `text`; a row
  carrying `expected_label` is rejected).
- `generate_data.py`: no randomness; produces `contract.toml` (4 known
  labels `billing`, `technical`, `sales`, `other`; routed labels the first
  three; threshold 0.90; `max_risk` 0.05; `min_coverage` 0.50; `alpha` 0.05;
  `evidence_scope = "demo"`), `calibration.jsonl` (12 labelled cases),
  `verification.jsonl` (160 labelled cases), `responses.jsonl` (fixture rows
  for all 160 cases and 8 tickets) and `tickets.jsonl` (8 label-free
  tickets). Rules and the prediction are in its docstring and the README.
- `recorded/a5fe090202f7/`: `PRODUCER.json` (format
  `actseal-action-gate-recorded-run/1`; `implementation_sha256`
  `a5fe0902...1642`; engine `actseal-choice-v1`; `lock_sha256`
  `cb009be0039afefd995f6eac3a8bd9767d6bf026a73273b47e87a51fc9fbd715`;
  `verdict_status` `PASS`; `source_commit`
  `76758d7084e396c8960718d28c1cad5fb70bac03`; `uv_lock_sha256`
  `4e1d8d9af9cf5610efc43844afc7838720602c2026648ffbc70585e761853189`; SHA-256
  of the four inputs; a note stating the data is synthetic and no model, key

  with sorted keys, which made `--check` and `--route` fail on the first
  recording; `check`/`route` gained a `recorded_root` parameter for tests;
  `--record` creates a missing parent. The authored data, policy and recorded
  bytes were not changed; `--check` verifies the recorded input hashes equal
  the committed inputs.
- The recorded run's `source_commit` is `76758d7` (the freeze commit, whose
  `src/actseal` equals main `77bf39f`), not a main commit, because the
  authored inputs did not exist on main. A reviewer can reproduce the records,
  faults and verdict from any commit with the same source fingerprint; the
  lock seal depends on the fingerprint.
- The example's "trusted channel" for the expected lock digest is
  `PRODUCER.json` beside the bundle. The README states explicitly that this
  is convenience for an example and that a deployed application must keep the
  digest in its own configuration (docs/threat-model.md).
