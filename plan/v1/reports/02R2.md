## Required changes applied

1. **P1, demo receipts violated the published schema.**
   `docs/schemas/cli-receipt.schema.json`: the former `VerifyPayload`
   (which required `exit_code` and `ok`) is replaced by `BundlePayload`:
   verdict fields plus `failures`, `warnings`, `faults` only. `VerifyReceipt`
   is `BundlePayload` plus `schema_version`, `command`, `exit_code`, `ok`,
   `out`; `DemoRun` is `BundlePayload` plus `expected_status`, `as_expected`,
   `lock`, `evidence`, `replay`, `replay_matches`, with
   `unevaluatedProperties: false`. CLI output was not changed.
   `docs/stability.md` receipt table now describes the `verify` and `demo`
   payloads in these terms (nested runs have no `exit_code`, `ok` or `out`).
   `docs/schemas/README.md` records the factoring and points at the new
   validation tests.
   New `tests/unit/test_schema_validation.py` (21 tests) uses
   `jsonschema.Draft202012Validator` with a local `referencing.Registry`
   built from the eight committed schema files (keyed by `$id`); no
   `retrieve` callable is supplied, so an unknown `$ref` raises
   `Unresolvable`/`NoSuchResource` instead of fetching (asserted). It
   validates: every schema file against the draft metaschema; every bundle
   file written by `write_bundle` (manifest, lock, verdict, every record row
   and its capture, every fault row and its capture) for fixture
   INCONCLUSIVE/PASS/BLOCK evidence, Laya INCONCLUSIVE evidence and an
   ADR 0009 infrastructure-ERROR bundle; both demo bundles and locks from a
   real `demo_run`; the packaged registry (plus seven malformed registries
   rejected); a synthetic 0.1.0 lock rejected by the schema-2 lock schema;
   every CLI receipt variant: `lock` success and destination-exists error,
   `verify` PASS and BLOCK, `replay` PASS/BLOCK with and without the expected
   digest, `replay` expected-digest mismatch, `replay` missing bundle,
   `replay` legacy bundle (with `notes`), `verify` legacy-lock error, usage
   error, abbreviated option, unparsable command, invalid provider choice,
   missing required option, `demo` success including both nested runs, `demo`
   prespecified-expectation failure (exit 3, status ERROR) and `demo`
   destination-exists error. Negative cases prove strictness: the exact
   REVIEW 02 shape (a nested run carrying `exit_code`) is rejected, as are a
   run carrying `ok`, unversioned or wrong-version receipts, extra fields on
   demo/verify receipts, wrong `exit_code` on lock/verify, an empty
   `replay_engine_version`, a missing `command`, non-array `notes`, a
   malformed `expected_lock_sha256` and a replay receipt without `notes`.
2. **P2, registry approvals in patch releases.** `docs/versioning.md`: the
   SemVer table now allows "reviewed compatibility registry entries approving
   an exact released source fingerprint for an existing engine" in a patch
   release; new engines remain minor. The approval section adds the rationale
   (every source change, including a patch, changes the fingerprint) and
   restates: explicit per-fingerprint approval, archived-evidence regression
   requirement, no wildcard, range or "all patches of" form.
3. **P2, `--version` is root-only.** `docs/stability.md` now states
   `--version` is a root-only option (`actseal COMMAND --version` is a usage
   error, `ERROR` 3) and that `-h`/`--help` is accepted at the root and every
   command; both remain text. The CLI inventory table row reads
   "`--version` (root only)". No CLI behaviour changed.
