Deviations from spec (with reason)

- Fault-violation BLOCK tests use a test seam: the accepted normalizer and
  policy never violate a canonical scenario (selected probability 0.0 always
  abstains, unknown labels always deny, failures always escalate), so the BLOCK
  branch is unreachable with the real authorities. Those tests wrap the
  evaluator imported by `assessment` to return a different action for exactly
  one canonical fault outcome, delegating every other call to the real
  `evaluate`. This simulates a defective policy; it does not replace a
  dependency, and a parallel test shows that the same claimed violation
  without the evaluator agreeing is `integrity.fault_decision` ERROR.
- Reason-code vocabulary within the frozen `integrity.<invariant>` family:
  `lock`, `records`, `request_hash`, `outcome`, `decision`, `faults`,
  `fault_request`, `fault_capture`, `fault_outcome`, `fault_decision`.
  `integrity.lock` short-circuits because record/fault checks against an
  invalid lock are meaningless; other codes accumulate.
- When faults violate and the statistics alone would PASS, the verdict is
  BLOCK with only `fault.<kind>` codes (no `contract.satisfied`). When
  statistics are BLOCK/INCONCLUSIVE their codes are kept alongside the fault
  codes as diagnostics. Counts/intervals in a fault BLOCK are the valid
  regular-evidence statistics; faults never enter n.
- `infrastructure.worker_invalidated` is reported only when every integrity
  check passes (the contract's "after integrity checks"); an incomplete or
  forged Laya run reports its integrity codes alone.
- Python type misuse (non-PlanLock, non-sequence, wrong element types) raises
  `SchemaError` instead of returning ERROR, consistent with the other modules.
- A fully re-authored lock (labels, inventory and seal all rewritten) is
  self-consistent and assesses against the new labels; the test records that
  only the externally anchored lock digest exposes it (ADR 0005), not assess.
